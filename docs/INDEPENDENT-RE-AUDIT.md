## 7. P0-1 — CWD-relative hook registration and state resolution

**Closed.**

- The registered command written into `.claude/settings.json` is
  `"C:\Program Files\nodejs\node.exe" "<project>\.grudge\bin\grudge.mjs" hook PreToolUse`.
  The script path is absolute, exists, and is 197,675 bytes.
- Running that exact registered command blocks (`exit 2`) from the project root, from a nested
  `nested\deep` subdirectory, and when the *process* cwd is a different directory entirely.
- Payload `cwd` values that are outside the install root, non-existent, or non-string all emit an
  explicit diagnostic and still block:
  `grudge: hook payload cwd '<x>' is outside the install root '<root>'; enforcing the rules installed at '<root>'`.
- The original failure mode is reproducible only the old way: invoking a relative
  `.grudge/bin/grudge.mjs` from a subdirectory fails (exit 1). Registration no longer does that.
- A missing `compiled.json` allows with no message. This is the correct empty-install state —
  `grudge setup` does not create that file, and `doctor` reports `compiled.json :: not present`
  as OK. A *corrupt*, wrong-version, or oversized `compiled.json` is never silent:
  `not a version 1 compiled file; ignored (fail-open)`, `over the 4194304-byte limit; ignored`,
  and an invalid rule is skipped with `project rule "bad" is invalid and was skipped`.
- `grudge doctor` on the installed CLI reports `hook paths :: absolute and present`,
  `hooks :: present`, `hook completeness :: all expected Claude Code events are registered`, and
  `hook scopes :: no duplicate user/project Grudge hook scopes detected` (19 checks, 0 failures).

All five registered hook events (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`,
`Stop`) use the same absolute node + absolute script form.

## 8. P0-2 — Global scope

**Closed.**

- `setup --scope global` writes an absolute command into `<home>/.claude/settings.json` and a
  runtime under `<home>/.grudge/bin/grudge.mjs`.
- One global rule blocks the matching call in two unrelated projects (A and B) and does not touch
  an unrelated call in B.
- A project rule applies only in its own project; it does not leak into B.
- Precedence is deterministic: a project rule that reuses a global rule id is ignored with
  `project rule '<id>' is ignored; the rule with that id from the other installation takes
  precedence`, and the global rule keeps blocking.
- `mode: "off"` is scoped per installation: project-off disables that project's rule but not the
  global rule; global-off disables the global rule but not an explicit project rule.
- Session state is per project: the same `session_id` written in A and B produces two separate
  `.grudge/session/<id>.jsonl` files containing only their own event.
- A repo install coexists with the global install and consumes both layers.

## 9. P0-3 — Budget cannot turn a block into an allow

**Closed.**

- With `hookBudgetMs: 1`, a matching call still returns **exit 2** and stderr says
  `state load took <n>ms, over hookBudgetMs 1; enforcement continued (fail-closed)`.
- The old fail-open string `hook time budget exceeded` is absent, and the shipped bundle no longer
  contains `withBudget` or `budget exceeded`.
- 20 concurrent hook processes under `hookBudgetMs: 1`: **20/20 exit 2**.
- A 6 MiB session history (6,294,020 B) still blocks in 25 ms; a stale lock and a held
  `stats.jsonl.lock` do not change the verdict; five timed calls all returned exit 2.
- Invalid budgets (`0`, `-5`, `"abc"`) warn (`hookBudgetMs <v> is invalid; using 1500.
  Enforcement is not affected.`) and still block.
- Fail-closed is explicit in the diagnostic, so the behaviour is both intentional and observable.

**Closed for the audited scope.**

The probe wrote real session files and inspected them on disk (`.grudge/session/p04*.jsonl`,

- `packages/grudge/package.json` = `0.2.0`, `package-lock.json` = `0.2.0`, `src/version.js` = `0.2.0`.
- `pyproject.toml` = `0.2.1`.

This is not a P0/P1 security defect. It is a release blocker because it breaks the commit's own

### O-1 — `grudge demo --fast` reports a scar path inside the installed package (observation)

Fast mode names `<venv>\Lib\site-packages\scars\sample_leak.scar.json` as the scar it replays.
The file ships in the wheel (12,430 B) and its mtime did not change across demo runs, so this is a

### O-2 — `stats --json` has no Stop counter (observation)

Stop events are written and deduplicated correctly, but the statistics command exposes no `stops`

### O-3 — Duplicate hook scopes are only diagnosed, not prevented (observation)

`doctor` reports `no duplicate user/project Grudge hook scopes detected`, and the current machine
has a user-level Grudge install plus project installs. No double-block was observed in the probes,

### O-4 — Generic scar text can make the agent refuse unrelated commands (test artefact)

In the live test, a synthetic rule whose English text was `Never run this exact command.` (no
token in it) caused the model to decline an unrelated `echo` in later turns. The hook itself
allowed the call (PreToolUse + PostToolUse recorded, stdout returned). Real proposals carry
concrete English, so this is an artefact of the synthetic rule, but it shows that scar wording
drives agent behaviour as much as enforcement does.

## 15. Remaining limitations

- **L-1** Only Windows was executed. macOS/Linux CI is configured but red for R-1, so no
  cross-platform evidence exists for this commit.
- **L-2** Node 25.2.1 was used; the package declares `>=18` and CI uses Node 20. Node 18/20 were
  not exercised.
- **L-3** Rule state was written directly to `.grudge/compiled.json` (the documented runtime
  interface) rather than through a full `propose` → `accept` cycle. `setup`, `doctor`, `stats`,
  `verify`, `scars`, and `hook` were exercised through the installed CLI.
- **L-4** The live model is non-deterministic: one re-prompt abandoned the tool call before
  invoking it (no hook event, no block); the enforcement evidence comes from the recorded
  PreToolUse/PostToolUse pair and the transcript of the blocked run.
- **L-5** Redaction is heuristic: labelled fields, URL query credentials, known key prefixes, and
  `AWS_*` assignments are covered; unlabelled high-entropy strings and prose (`my password is X`)
  are not. This matches the P0-4 scope but is not “all secrets”.
- **L-6** Deleting `.grudge/compiled.json` (or the whole `.grudge` directory) removes enforcement
  with no hook-path diagnostic, because an empty install is a valid state. `doctor` can show the
  state, but nothing detects “rules were deleted”.
- **L-7** All evidence was produced under `D:\Temp\opencode\rea`; the probes are not part of the
  repository. The commit export, virtualenv, and npm install tree were deleted afterwards to leave
  the machine clean; the probe scripts, result JSONs, built wheel/tarball, and captured outputs
  were kept there. The matrix records every command so the runs can be recreated.

## 17. Conclusion

The enforcement remediation is real. Absolute hook registration, global layering with per-scope
`mode`, fail-closed budgets under load, on-disk redaction, and Stop statistics all behave as
claimed when driven through artifacts built from `0e06293`. The commit is not releasable as-is
because its own version metadata disagrees with itself, which fails its test suite and release
gate. Commit the `0.2.1` bump that already exists in the working tree (or revert `pyproject.toml`
to `0.2.0`), re-run `python -m pytest` and `python scripts/release_check.py`, and the branch can
move to user acceptance testing.

**Final verdict: FAIL — BLOCKERS REMAIN** (blocker R-1: release metadata/version consistency).
